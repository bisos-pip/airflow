Where =bisos.airflow= sits among the ways of running Airflow, and how its systemd units
are arranged. For the full layout (account, directories, environment, metadata DB,
exposure, commands) see the [[file:../../airflowUsage/_nodeBase_/fullUsagePanel-en.org][airflowUsage]] panel.

*** Deployment Options

Airflow can be set up along a spectrum of scale and isolation. The rows below are
size/scope profiles; the columns are *how the Airflow processes are supervised*.

|----------------+---------------------------------+---------------------------------+---------------------------------|
| /              | <                               |                                  |                                 |
|  Scale \\ Supervision | =userSelf= (manual/foreground)  | =systemd= (host-native units)    | =container= (docker/podman/k8s)  |
|----------------+---------------------------------+---------------------------------+---------------------------------|
| small-dev      | =airflow standalone= in a shell  | single dev-mode systemd unit     | one all-in-one container image   |
| standalone     | =airflow webserver=/=scheduler= by hand | *what we have for airflow.here* → | podman/docker-compose, one host  |
| largescale     | not applicable                  | systemd units per host, Celery/K8s executor across many hosts | Kubernetes / managed Airflow (MWAA, Composer, Astronomer) |
|----------------+---------------------------------+---------------------------------+---------------------------------|

*What we have for =airflow.here=* is the *standalone × systemd* cell: a single host with
no Celery/Redis, each Airflow role planted as its own =systemd= unit via a CBS/CBM
(=airflow-cbs.pcs= / =cbmProc-airflow.spcs=), rather than one monolithic
=airflow standalone= process. This gives independent start/stop/status and independent
logs per role, without the operational overhead of a distributed executor or
containers. The package does not set the executor; a single-host instance normally
runs =LocalExecutor=, set in its own =airflow.cfg=.

*** The 5 systemd Units and DB Init

Five planted =*-sysd.pcs= units live in =py3/bin/=, all delegating to the same
=airflow= CLI executable (via =systemd_seedInfo.setup()=), each running a different
sub-command. All five run as =User=airflow= / =Group=airflow= and take their
environment (=AIRFLOW_HOME=/opt/airflow=, the PostgreSQL connection string, the
Airflow 3 API URLs) from =EnvironmentFile=/etc/default/airflow=.

| Unit (=.pcs=)                         | Airflow role                 | =ExecStart= sub-command          | Type                             | Ordering                                   |
|---------------------------------------+------------------------------+----------------------------------+----------------------------------+--------------------------------------------|
| =airflow-db-sysd.pcs=                 | DB migration                 | =airflow db migrate=             | =oneshot=, =RemainAfterExit=yes= | =Requires=/=After=postgresql.service=      |
| =airflow-webserver-sysd.pcs=          | API server + web UI          | =airflow api-server --port ...=  | long-running                     | =Requires=/=After=airflow-db.service=      |
| =airflow-scheduler-sysd.pcs=          | Scheduler                    | =airflow scheduler=              | long-running                     | =Requires=/=After=airflow-db.service=      |
| =airflow-triggerer-sysd.pcs=          | Triggerer (deferrable tasks) | =airflow triggerer=              | long-running                     | =Requires=/=After=airflow-db.service=      |
| =airflow-dag-processor-sysd.pcs=      | DAG file parsing             | =airflow dag-processor=          | long-running                     | =Requires=/=After=airflow-db.service=      |

=airflow-db-sysd.pcs= is a =oneshot= unit with =RemainAfterExit=yes=: once PostgreSQL is
up, it runs =airflow db migrate= to bring the metadata schema up to date, then reports
itself "active" without staying resident. The four long-running units each declare
=Requires=/=After=airflow-db.service=, so systemd guarantees the migration has been
attempted before any of them starts --- avoiding races against an un-migrated database
on a fresh host.

=airflow-dag-processor= is required on Airflow 3, which parses DAG files in a standalone
process rather than in the scheduler. Without it every unit is healthy and no DAG is
ever registered.

All five are planted via the CBS/CBM pattern: =airflow-cbs.pcs= declares the bundle
(sbom + these five sysd units + assemble for DNS/vhost) and the CBM leaf
=sys/cbm/collective/hereWeb/airflow/cbmProc.spcs= materializes it on this host. See the
=sysd-pcs-authorship= and =cbm-authorship= skills for the underlying mechanics.

*** Not a Manual Recipe

This panel used to end with a hand-run installation recipe. It came from before the
package existed: =~/airflow=, a hand-made venv, a password-bearing PostgreSQL user and
=airflow db init=. It was removed on 2026-10-01 because it contradicted what the package
does. Install with =airflow-sbom.pcs -i sbom_fullUpdate=, or materialize the whole
bundle through the CBM leaf; see [[file:../../airflowUsage/_nodeBase_/fullUsagePanel-en.org][airflowUsage]].
